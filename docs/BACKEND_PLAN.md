# AVR Borrowing System: Backend Plan

## Purpose and current limitations

The app currently stores borrowing data in browser session storage and accounts and login sessions in local storage. Those records are local to a browser, can be altered by the user, and cannot be shared between devices. The demo staff account is also seeded in the browser. A backend must become the source of truth for account identity, roles, inventory, loans, history, and notifications.

This document is a proposal only. No source files or application behavior are changed by this plan.

## 1. Stack options

| Option | Advantages | Trade-offs |
| --- | --- | --- |
| **Supabase (PostgreSQL, Auth, Row Level Security, scheduled functions)** | Fastest path for a small student team; managed database and authentication; SQL and a relational schema; built-in email integrations and deployment. | Team must learn Supabase policies and service boundaries; security depends on correct Row Level Security policies; custom workflows and scheduled jobs may require Edge Functions or an external scheduler; provider coupling. |
| **Node.js + Express + PostgreSQL** | Familiar JavaScript end-to-end; explicit server-side role checks and business rules; complete control over API, cookie sessions, jobs, and deployment. | More code and operational responsibility: server hosting, migrations, session storage, email delivery, monitoring, and database backups. |
| **Managed Node/PostgreSQL platform (for example, a university-supported host)** | Keeps the explicit API design while outsourcing some infrastructure and database operations. | Availability, cost, supported runtimes, and university data policies need confirmation; may still require separate email and scheduler services. |

**Initial recommendation:** choose Supabase if the priority is delivering a secure, cross-device prototype with limited operations work, and the team is comfortable enforcing access with database policies plus server-side functions for sensitive operations. Choose Express + PostgreSQL if the team needs to demonstrate a conventional API or expects substantial custom workflows. In either case, the browser must never be trusted to assign roles, decide availability, enforce borrowing limits, or write arbitrary history records.

**Decision needed:** Which option should implementation target—Supabase, Node/Express + PostgreSQL, or a specific university-supported platform?

## 2. Proposed PostgreSQL schema

Use UUID primary keys for database entities. Keep the existing human-readable equipment asset ID and loan ID as unique business identifiers. Store timestamps as `timestamptz` in UTC; convert to the AVR desk's configured local timezone for opening-hour validation and display. Store role and status values as checked text or PostgreSQL enums with migrations for future values.

### `users`

| Field | Type | Rules / purpose |
| --- | --- | --- |
| `id` | `uuid` | Primary key; generated by the database or auth provider. |
| `email` | `citext` or normalized `varchar(254)` | Required, unique; normalized to lowercase. |
| `name` | `varchar(160)` | Required. |
| `role` | `text` | Required, check in `student`, `staff`, `admin`; never accepted from public registration input. |
| `password_hash` | `text` | Required for local-password authentication; Argon2id or bcrypt encoded hash. Omit if authentication is delegated to a provider. |
| `created_at` | `timestamptz` | Required, default `now()`. |
| `updated_at` | `timestamptz` | Required, default `now()`. |
| `disabled_at` | `timestamptz` | Nullable; disables an account without deleting its audit history. |

Indexes/constraints: unique normalized email; index on `(role, disabled_at)`. Require `@uic.edu.ph` for student registration on the server. Provision staff/admin users only through an authorized admin workflow.

### `equipment`

| Field | Type | Rules / purpose |
| --- | --- | --- |
| `id` | `uuid` | Primary key. |
| `asset_id` | `varchar(80)` | Required, unique case-insensitively; corresponds to the current front-end equipment `id`. |
| `name` | `varchar(200)` | Required. |
| `category` | `varchar(100)` | Required. |
| `location` | `varchar(200)` | Required. |
| `status` | `text` | Required; `available`, `reserved`, `checked-out`, or `maintenance`. |
| `created_at`, `updated_at` | `timestamptz` | Required; defaults/update behavior as above. |

Indexes: unique index on `lower(asset_id)`; index on `(status, category)` for inventory filters.

### `loans`

| Field | Type | Rules / purpose |
| --- | --- | --- |
| `id` | `uuid` | Primary key. |
| `loan_code` | `varchar(32)` | Required, unique, human-readable `AVR-<year>-<number>` pickup code. Allocate atomically (see below). |
| `equipment_id` | `uuid` | Required FK to `equipment.id`. |
| `user_id` | `uuid` | Required FK to `users.id`; authoritative owner. |
| `student_name_snapshot` | `varchar(160)` | Required name as recorded at request time. |
| `student_email_snapshot` | `varchar(254)` | Required email snapshot for historical display and notification; access remains role-controlled. |
| `student_id` | `varchar(100)` | Nullable; optional manually entered student ID. |
| `room` | `varchar(160)` | Required borrowing location. |
| `status` | `text` | Required; `reserved` or `checked-out` for active loans. |
| `created_at` | `timestamptz` | Required; reservation creation time and expiry basis. |
| `borrowed_at` | `timestamptz` | Required; set at request and updated to pickup time on release, preserving current behavior. |
| `return_at` | `timestamptz` | Required; requested return deadline. |
| `closed_at` | `timestamptz` | Nullable; set when cancelled or returned. |

Indexes/constraints: unique `loan_code`; index on `(user_id, status)`; index on `(status, return_at)` for overdue/expiry jobs; partial unique index on `equipment_id` for active statuses (`reserved`, `checked-out`) to guarantee one active loan per item. Add a check that `return_at > created_at`.

The current application removes a loan from its active list after cancellation or return. The database should retain the loan and transition it to a terminal status (for example `cancelled` or `returned`) so events, notifications, and foreign keys stay consistent. Active-loan API responses should filter to `reserved` and `checked-out`.

### `loan_events` (history / audit trail)

| Field | Type | Rules / purpose |
| --- | --- | --- |
| `id` | `uuid` | Primary key. |
| `loan_id` | `uuid` | Required FK to `loans.id`. |
| `actor_user_id` | `uuid` | Nullable FK to `users.id`; null only for system-generated events. |
| `action` | `text` | Required; examples `Reserved`, `Picked up`, `Cancelled`, `Returned`. |
| `equipment_name_snapshot` | `varchar(200)` | Required snapshot so later equipment renames do not rewrite history. |
| `student_name_snapshot` | `varchar(160)` | Required snapshot. |
| `student_email_snapshot` | `varchar(254)` | Required snapshot. |
| `room_snapshot` | `varchar(160)` | Required snapshot. |
| `condition` | `text` | Nullable; `good`, `damaged`, or `missing-parts`, recorded on return. |
| `notes` | `text` | Nullable; staff return notes. |
| `created_at` | `timestamptz` | Required, default `now()`. |

Indexes: `(loan_id, created_at DESC)`, `(created_at DESC)`, and `(student_email_snapshot, created_at DESC)` for history filtering. Events are append-only; clients cannot create arbitrary events.

### `notifications`

| Field | Type | Rules / purpose |
| --- | --- | --- |
| `id` | `uuid` | Primary key. |
| `recipient_user_id` | `uuid` | Nullable FK to `users.id`; null may represent a staff-wide notification. |
| `kind` | `text` | Required; for example `request`, `return`, `overdue`, `cancelled`, `reservation-expired`. |
| `title` | `varchar(200)` | Required. |
| `message` | `text` | Required. |
| `loan_id` | `uuid` | Nullable FK to `loans.id`. |
| `read_at` | `timestamptz` | Nullable; null means unread. |
| `created_at` | `timestamptz` | Required, default `now()`. |

Indexes: `(recipient_user_id, read_at, created_at DESC)` and `(created_at DESC)`. Determine whether staff alerts are shared or per-staff recipient based on the team's desired notification behavior.

### Atomic borrowing transaction and collision prevention

Implement borrowing in one database transaction, exposed through a server endpoint or a PostgreSQL function. Within the transaction:

1. Lock the requested equipment row with `SELECT ... FOR UPDATE`; reject if it is not `available`.
2. Lock the student's user row (or use a transaction-scoped advisory lock keyed by `user_id`) so simultaneous requests cannot both pass per-student limits.
3. Validate the authenticated owner, item status, active loan limit (3), overdue checked-out loans, return-time lead (15 minutes), maximum duration (168 hours), and local desk hours (08:00–17:00). The server's timezone configuration is authoritative.
4. Allocate a loan code using a dedicated `loan_code_counters` table keyed by year, incremented with `INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING`. A database sequence may also be used if gap-free numbers are not required. Do not derive uniqueness from the clock.
5. Insert the `reserved` loan, change equipment to `reserved`, append a `Reserved` event, and create the staff notification.
6. Commit together. Any validation or write failure rolls back all changes.

The partial unique index on active `equipment_id` remains the final defense against duplicate active loans, including requests that do not follow the expected lock path. Use the same transaction pattern for release, cancellation, and return so equipment, loan state, event, and notification cannot become inconsistent.

## 3. REST API and authorization

All endpoints require HTTPS. Authenticated endpoints derive the user and role from the verified session/token, never from a submitted `role`, `email`, or client-side context. `student-owner` below means a student may access only their own records. `staff/admin` means either staff or admin. `admin` is restricted to account provisioning and administrative functions.

### Authentication (`AuthContext`)

| Method and path | Purpose | Access |
| --- | --- | --- |
| `POST /api/auth/register` | Create a student account and authenticated session; validate `@uic.edu.ph`, name, password, and duplicate email. | Public; creates `student` only. |
| `POST /api/auth/login` | Verify credentials and establish session. | Public. |
| `GET /api/auth/session` | Restore the current session/user at app startup. | Authenticated. |
| `POST /api/auth/logout` | Revoke/destroy current session. | Authenticated. |
| `POST /api/auth/password-reset-requests` | Send a single-use, time-limited reset link without revealing whether an account exists. | Public; eligible accounts only. |
| `POST /api/auth/password-resets` | Validate reset token and update password/revoke other sessions. | Public with valid reset token. |
| `POST /api/admin/users` | Create/invite staff or admin accounts; audit the actor and assigned role. | Admin only. |
| `PATCH /api/admin/users/:userId/role` | Change a staff role if role management is required. | Admin only; optional initial scope. |

### Borrowing and equipment (`BorrowingContext`)

| Method and path | Purpose | Access |
| --- | --- | --- |
| `GET /api/equipment` | List equipment; student responses expose only items safe to display (available items for the borrow picker, plus any specifically needed public inventory). | Authenticated; response filtered by role/use. |
| `POST /api/equipment` | Add an item, initially `available`. | Staff/admin. |
| `PATCH /api/equipment/:equipmentId` | Update name, category, or location; asset ID is immutable. | Staff/admin. |
| `PATCH /api/equipment/:equipmentId/status` | Set `available` or `maintenance`; reject active reserved/checked-out items. | Staff/admin. |
| `GET /api/loans?scope=mine\|active` | List own loans for students or active loans for staff; status can be filtered. | Authenticated; students see own only, staff/admin may see all active. |
| `POST /api/loans` | Create reservation using the authenticated user; body includes `equipmentId`, `returnAt`, `room`, optional `studentId`. Server obtains name/email from the account. | Student; transaction and rules above. |
| `GET /api/loans/:loanId` | Fetch one loan for confirmation or pickup details. | Student-owner or staff/admin. |
| `POST /api/loans/:loanId/release` | Transition reservation to checked out, update `borrowed_at`, equipment, event, and notifications. | Staff/admin. |
| `POST /api/loans/:loanId/cancel` | Cancel reservation and release equipment. | Student-owner or staff/admin. |
| `POST /api/loans/:loanId/return` | Return checked-out item with `condition` (`good`, `damaged`, `missing-parts`) and optional `notes`; set item status and record event/notification. | Staff/admin. |
| `GET /api/loan-events` | Search/filter history by text, action, date; server scopes student results to owner. | Authenticated; students own only, staff/admin all. |
| `GET /api/notifications` | List notifications visible to current user/role. | Authenticated; server scopes recipients. |
| `PATCH /api/notifications/:notificationId/read` | Mark an accessible notification as read. | Authenticated; owner or staff/admin for shared staff notifications. |

For dashboard metrics and staff inventory filters, either calculate counts from the role-filtered equipment/loan lists already fetched or add `GET /api/dashboard/summary` for a consistent server-side aggregate. Do not let a client-submitted email widen a query. The current `studentEmail`, `studentId`, and `confirmedLoanId` context fields are UI workflow state, not server identity; retain only the fields still needed by pages, or derive confirmation from the route and API response.

## 4. Authentication and security design

- Store only a slow password hash: prefer **Argon2id** with a maintained library and deployment-compatible parameters; bcrypt is an acceptable alternative if Argon2id support is unavailable. Never use unsalted SHA-256.
- For a same-origin web app, prefer an opaque server-side session in a persistent session store (PostgreSQL or Redis) with a `Secure`, `HttpOnly`, `SameSite=Lax` cookie, session rotation at login, expiration, logout revocation, and CSRF protection for state-changing requests. If a separate API/client requires JWTs, use short-lived access tokens and rotated, revocable refresh tokens stored securely; do not put long-lived bearer tokens in local storage.
- Enforce role and ownership checks on every API request and again in database policies where supported. A route guard in React improves UX only; it is not authorization.
- Validate the exact normalized email domain at registration on the server, reject role fields on public registration, and use uniqueness constraints to handle concurrent registrations.
- Password reset uses cryptographically random, single-use, hashed tokens with short expiry; rate-limit login, registration, and reset requests; return generic reset responses.
- Staff and admin accounts are created by an admin through an audited invite/provisioning endpoint. Remove the hard-coded demo staff password before production; development seed accounts must be isolated to non-production environments and use environment-provided credentials.
- Apply input validation, parameterized queries, request size limits, secure headers, rate limits, structured audit logging, and generic external error messages. Never log passwords, tokens, reset links, or session cookies.

## 5. Incremental migration with a stable context API

The goal is to keep page imports and public context method names stable while replacing local mutations with calls through a small `src/lib/api.js`. This phase's implementation should first agree on API shapes and auth choice; `api.js` should provide a typed/consistent response and surface server errors rather than silently falling back to browser data.

1. **Backend foundation:** select stack and hosting; create schema migrations, constraints, seed/import strategy, and health checks. Build auth and API tests before changing the UI.
2. **Define API contract:** document JSON request/response shapes for each endpoint above, error codes/messages, pagination, and server role policy. Preserve current useful public context methods such as `borrowEquipment`, `returnEquipment`, `releaseLoan`, and `cancelReservation`.
3. **Add `src/lib/api.js`:** centralize `fetch`, credentials (`credentials: 'include'` for session cookies), JSON encoding, error parsing, and optional request cancellation. Do not put secrets or trusted roles in browser code.
4. **Move `AuthContext` to the server:** have startup call `GET /api/auth/session`; have `login`, `register`, and `logout` call the corresponding endpoints and update context user/readiness. Remove local account/session credential authority and the browser-seeded demo account only as part of the coordinated auth cutover.
5. **Replace `BorrowingContext` initialization:** load equipment, active loans, history, and notifications from the API after authentication/readiness. Keep the same exposed state and action names to avoid page changes. For a multi-request load, present a clear loading/error state rather than seeding browser data as if it were authoritative.
6. **Replace mutations one at a time:** map add/update/status to equipment endpoints; borrow to `POST /api/loans`; release/cancel/return to their action endpoints; read notifications to the notification endpoint. Preserve established return shapes where feasible (`{ ok: true }`, `{ error }`) and translate server validation errors consistently.
7. **Refresh shared data:** after a successful action, refresh affected context collections or update them from authoritative server responses. Start with explicit refetching; add polling or server-sent updates only if the team needs near-real-time behavior. The current 60-second local reservation timer must be removed after server expiry is active.
8. **Migrate browser-only data:** if demo data needs to be retained, create a one-time, reviewed admin import with conflict reporting and a backup. Do not upload localStorage records automatically from every student's browser; those records are not authoritative and may conflict or contain tampered roles/data.
9. **Cut over and verify:** deploy backend and database, provision users and staff, verify one-student ownership, role restrictions, simultaneous borrowing, status transitions, expiry, and recovery; then remove reads/writes of auth and borrowing data in local/session storage. Keep only non-sensitive UI preferences client-side.

## 6. Scheduled jobs and email

- **Reservation expiry:** run a server job at least once per minute (or use a database-backed scheduler) to select `reserved` loans whose `created_at <= now() - interval '2 hours'`. Lock each candidate, recheck status, mark it `cancelled`, return equipment to `available`, append a system `Cancelled`/`Reservation expired` event, and create a notification in one transaction. Make the job idempotent so retries cannot cancel twice.
- **Overdue detection:** periodically query `checked-out` loans whose `return_at < now()` and which have no prior overdue notice for the relevant threshold. Record a notification/event or a deduplication marker so each reminder is sent once per schedule.
- **Email reminders:** choose reminder timing (for example, first notice when overdue and recurring daily reminders) with the AVR team. Send through an approved university SMTP or email provider. Queue messages transactionally (outbox table/queue) and retry delivery without duplicating events. Avoid including sensitive details beyond what the recipient needs.
- Use the backend's configured timezone for desk policy and a single consistent UTC clock for persistence and job comparisons.

## 7. Deployment and configuration

Deploy the SPA and backend behind HTTPS, with the API ideally same-origin (or tightly restricted CORS if separate). Use managed PostgreSQL backups and point-in-time recovery where available. Apply schema migrations as a controlled release step, not at application startup. Configure staging and production separately; production must not seed demo accounts or sample personal data.

Suggested server-side environment variables (exact names depend on the selected platform):

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | PostgreSQL connection string; use TLS and a least-privilege database role. |
| `SESSION_SECRET` | High-entropy secret for signing/encrypting session identifiers if required by the session framework. |
| `APP_ORIGIN` | Canonical frontend origin for cookie, CSRF, and email-link validation. |
| `DESK_TIME_ZONE` | AVR desk IANA timezone used for borrowing rules and display policy. |
| `EMAIL_PROVIDER_URL` / `SMTP_HOST` | Approved email transport configuration. |
| `EMAIL_PROVIDER_API_KEY` / `SMTP_USER` / `SMTP_PASSWORD` | Secret credentials, stored in the deployment secret manager only. |
| `PASSWORD_RESET_BASE_URL` | Public reset-page base URL; never a secret. |
| `LOG_LEVEL` | Server logging verbosity. |
| `NODE_ENV` | Set to `production` for production behavior; disable demo seeding. |
| `CORS_ALLOWED_ORIGINS` | Exact frontend origins if frontend and API are on different origins. |
| `DEMO_STAFF_EMAIL` / `DEMO_STAFF_PASSWORD` | Development-only seed inputs if a demo account is still needed; never commit them or enable production seeding. |

For Supabase, store the project URL and publishable/anon key in frontend configuration only as intended by Supabase, and keep the service-role key exclusively in server-side secrets. Never expose database passwords, mail credentials, session secrets, or service-role keys in Vite `VITE_*` variables.

Operational checklist: HTTPS and secure cookies; database backups and restore test; migrations and rollback procedure; error monitoring; audit logs; rate limits; email delivery monitoring; secret rotation; and a documented account-provisioning/offboarding process.

## Questions before implementation

1. Which backend stack should the team use: Supabase, Node/Express + PostgreSQL, or a university-supported platform? Where will it be hosted?
2. Should the app use server-side cookie sessions (recommended for a same-origin web app), or is a separate API/client requirement driving JWTs?
3. What is the AVR desk's IANA timezone, and should 5:00 PM be an allowed return time (the current client rule allows exactly 17:00)?
4. Should staff notifications be shared among all staff, individually assigned, or both? Should students receive notifications too?
5. Which email provider is approved, and what overdue reminder schedule should be used?
6. Who will be the initial admin, and how should the demo data and demo staff account be treated during cutover?
7. Should cancelled and returned loans remain as terminal rows in `loans` (recommended for referential integrity), or does the team require hard deletion from the active-loan table?
8. Is student ID optional and informational only, or must it be validated against a university roster?
9. What pagination, retention, and audit-history access limits are required for the first release?
